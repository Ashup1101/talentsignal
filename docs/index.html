What it does

Your resume, read against the market

Every number comes from postings collected nightly by the pipeline. No LLM: the same skill patterns run on postings and on resumes, so the comparison is like for like.

Resume analysis

A PDF is parsed in memory (pdfplumber) and matched against a 110-skill dictionary, the same regex patterns the Spark pipeline runs on postings. Out come the match % per role and a salary estimate. Nothing is stored or logged.

pdfplumberregex dictionary~1 s per resume

Salary intelligence

An XGBoost model trained on 333 salaried postings, validated with 5-fold cross-validation grouped by employer. Its error is $35.7K, 20% lower than a per-role median ($44.4K) and 9% lower than role × seniority. Tracked in MLflow.

XGBoostGroupKFoldMLflow

Job matching

Semantic search with sentence-transformers (all-MiniLM-L6-v2, 384 dimensions). Long descriptions are chunked and averaged. Cosine similarity runs against the collected postings, and roles near your level come first.

embeddingscosine similaritylevel-aware

Skill demand

Each skill's share of a role's postings, ranked, with the most in-demand skills missing from your resume. A Prophet forecast is gated until a series has 12 weekly collections (3 so far), so it never forecasts from too little data.

demand rankProphetgated forecast

Orchestration

An Airflow 3 DAG runs the pipeline every night: 9 tasks in about 3½ minutes.

  • fetch → clean → skills → load → NLP
  • dbt source freshness, then dbt build
  • salary model and forecast in parallel
  • each task in its own process (PyTorch and XGBoost never share one)

Privacy by design

  • Resume sent as a raw body: no multipart temp files
  • nginx keeps uploads in memory, never on disk
  • Nothing logged; the response never echoes the text
  • Read-only database user for the app
How it ships

Merge to main, live minutes later

Seven checks on every pull request. On main, the images are published and the server deploys them itself, about a minute later. No SSH, and no AWS keys in CI.

Pull requestpytest, dbt on a throwaway Postgres, DAG imports, ML, API, web, Docker images + HTTPS modes
PublishOn main: API and web images pushed to GHCR, tagged with the commit
Server pullsA systemd timer checks every 2 minutes and deploys a new commit
DeploySettings from SSM, images, compose up --wait, HTTPS health check
Smoke testCI waits for the live commit, then tests TLS, pages, API and a sample resume

Ports 80 and 443 only. No SSH; one-off commands run through AWS Systems Manager.

Pull-based CD. The AWS organization blocks GitHub OIDC, so the server watches the registry instead of CI holding keys.

HTTPS by default. Let's Encrypt via certbot, renewed by a timer; nginx switches to TLS by itself.

Build log

Six phases, one at a time

Rebuilt from a one-paragraph description, with every decision written down and every number measured.

1

Ingestion: JSearch API + BLS → S3

A budget-aware fetcher (daily share, weekly role rotation, a hard stop on the API's remaining quota) landing raw JSON in S3, idempotent per day.

2

PySpark processing: clean, dedup, skills, Delta Lake

An explicit schema, annualized salaries, two-pass deduplication, and skill extraction through a pandas UDF.

3

dbt star schema: 19 models, 86 tests

Staging, intermediate and marts over RDS PostgreSQL. Salary associations are computed within each role, and CI builds everything against a throwaway Postgres.

4

Airflow 3 orchestration: a 9-task nightly DAG

Every step is a separate process calling the same CLI you run by hand; retries, timeouts and parallel model tasks.

5

NLP + ML: spaCy, embeddings, BERTopic, XGBoost, Prophet

Years of experience extracted for 74% of postings, topics from posting meaning, a salary model judged against three baselines, and a forecast that waits for enough data.

6

Web app + deployment: FastAPI, Next.js, Docker, EC2, HTTPS, CI/CD

A typed API and a static frontend, containerized behind nginx with Let's Encrypt, nine CI jobs, and a server that deploys each release itself.

Interesting problems solved

Where the data pushed back

Confounding by role

The "Excel penalty" was mostly role mix

−$60Kall postings
→
−$12Kwithin data analysts

Postings mentioning Excel paid far less overall, but mostly because analysts ask for Excel, and analysts earn less. Compared within one role, the gap shrinks to a fifth. It's a Simpson's-paradox-style trap.

Fix: every salary association is computed within one role, needs at least 10 salaries per side, and is worded "associated with", never "causes".

Silent data drift

The same job, a new ID every fetch

0 / 728repeated IDs across sightings

JSearch issues a new job_id each time it returns a posting, so IDs never repeat. Keeping the newest copy quietly moved re-seen postings into later weeks and rewrote demand history.

Fix: a job_sightings table, one row per posting per collection recorded before dedup, so past weeks never change.

Native crash

PyTorch + XGBoost = segfault

exit 139two OpenMP runtimes, one process

Both bring their own OpenMP runtime. In one process they crashed with exit 139, even with XGBoost on one thread; two OpenMP threads still crashed. It was isolated with separate-process experiments.

Fix: OMP_NUM_THREADS=1, pinned in code and baked into the Docker image's ENV, guarded by a regression test.
